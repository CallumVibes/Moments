# Moments OPRF server

Stretches a user's PIN without ever learning it, so that a 6-digit PIN can
safely unlock an account.

## Why a server exists at all

A PIN has roughly 20 bits of entropy. No amount of local key stretching saves
it — whoever holds the ciphertext simply tries all million candidates. A PIN is
only safe if **guessing requires asking someone who can say no.**

That is this server's entire job. It holds a secret scalar `k` and answers one
question: given a curve point `B`, what is `k·B`? The client blinds its point
with a fresh random scalar first, so `B` is uniformly random: the server learns
nothing about the PIN and cannot link two requests for the same one.

## Run two of them, under different operators

**This is a security requirement, not a deployment preference.**

A single operator can brute-force every PIN. It knows `k`, so for any candidate
PIN it can compute that candidate's OPRF output itself, derive the enrollment's
locator, and fetch the blob from a public relay — offline, with no rate limit in
the way. The client folds two servers' outputs together:

```
root = KDF(k_A·P ‖ k_B·P)
```

so neither operator alone can compute the root, and neither alone can grind.
**The safety of a PIN rests on those two operators not colluding.** Two
endpoints on one provider's infrastructure are one operator wearing two hats.

## Running it

```sh
node oprf-server.mjs --genkey          # print a fresh key
OPRF_KEY=<64 hex> PORT=8787 node oprf-server.mjs
```

No dependencies. `vendor-secp256k1.mjs` is generated by the app's own
`npm run build`, from the very bundle the browser runs, so both sides share one
curve implementation.

| Variable | Default | Meaning |
|---|---|---|
| `OPRF_KEY` | *(required)* | 64 hex chars. **Losing it destroys every PIN enrollment.** |
| `PORT` | `8787` | Listen port |
| `OPRF_BURST` | `10` | Attempts per tag per 10 minutes |
| `OPRF_DAILY` | `60` | Attempts per tag per 24 hours |
| `OPRF_ORIGIN` | `*` | Set this to your app's origin in production |

## Before you put this in production

- **The rate limit is the security boundary.** The in-memory limiter is correct
  for a *single process only*. Behind two or more instances it is a hole — an
  attacker spreads guesses across them. Back it with shared persistent storage
  (Redis, or your platform's KV) before scaling out.
- **Back up `OPRF_KEY`,** and keep it out of logs and crash dumps. The server
  logs only a fingerprint of it.
- **Pin `OPRF_ORIGIN`** rather than leaving it `*`.
- Put it behind TLS. The blinded point is not secret, but the rate-limit tag is
  linkable to an account over time, and a network observer should not collect it.

## Known limitations

- **Not a verifiable OPRF.** A malicious server can return a wrong point. The
  consequence is that unlocking fails, not that a key leaks — the client folds
  in a second server's output, which a single bad actor does not know. Adding a
  DLEQ proof would turn silent failure into detectable misbehaviour.
- **The tag is linkable.** It is `SHA-256` of a domain separator and the user's
  handle, so the server can count attempts per account and therefore sees that
  *some* account is being accessed, and how often. It never sees the handle, the
  PIN, or the npub. This is the minimum needed for a lockout to exist at all.
- **A known handle can be locked out on purpose.** The rate-limit tag is derived
  from the user's handle, and handles are guessable, so anyone can spend a
  victim's attempt budget and keep their PIN unlock unavailable. This is
  inherent to rate-limiting per account without an authenticated session: the
  limit has to key on *something* the client asserts. The lockout is temporary
  (it decays with the window) and never blocks the other recovery factors, which
  is a further reason the app refuses to let a PIN stand alone. Per-IP limits on
  top help against a single source but not a distributed one.
- **Enrollment spends budget too.** A user who mistypes while setting a PIN up
  draws down the same allowance as a failed unlock.
- **Availability is a real dependency.** If either server is down, PIN unlock
  fails closed; if either loses its key, every PIN enrollment is dead. This is
  why the app never lets a PIN be a user's only recovery factor.
